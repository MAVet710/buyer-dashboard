## Publication controls

- Keep beta qualification close to workflow and integration descriptions. An obscure footer caveat is insufficient.
- Use textual integration readiness instead of vendor-logo endorsement. Configuration, validation, provider acceptance and successful reconciliation are different states.
- Treat metrics inside a demo as sample data, prominently labeled. They are not measured customer outcomes.
- Use real UI captures only after data review. Never publish tenant identifiers, license IDs, credentials, customer names, employee data or raw regulatory records.
- Prefer a proposed beta evaluation sequence (understand the operation, map data and roles, validate selected workflows) to a promised migration/support service.
- Future proof records must contain company, person, role, quote/logo/result, state, license type, evidence URL or approved internal record, approval state and review date. Render only verified and explicitly publication-approved records.
- Re-review this ledger when capabilities change; do not automatically upgrade claims from a passing unit test, a merged adapter, or a configured credential.
