# Cultivation intelligence architecture

Implementation candidate, 2026-09-26. Primary owns review, PostgreSQL release gates, integration, commits, CI and deployment. This document is not a release assertion.

## Canonical boundaries

React and FastAPI remain the operator architecture. New records model relationships: crop cycles, actual canonical plant memberships, half-open occupancy/stage intervals, immutable approved recipe versions, connection configuration, device mapping revisions and operator events. Canonical rooms, plants, nursery groups, harvests, post-harvest records, Work, cost entries and the operational audit ledger remain authoritative. No inventory, harvest, financial or compliance ledger is copied. The draft cloud raw rollup, deviation and retention tables were removed; the edge owner provides that implementation.

Legacy manual telemetry remains in `cultivation_environment_observations`. Dictionary, validated-model and HTTP paths preserve source metric/value/unit before normalization. Approved canonical-equivalent retries preserve first evidence. Old originals remain null, exposed with `unavailable_historical` provenance. The controlled registry preserves `temperature` and `co2` and accepts their declared aliases. Default snapshots retain the original eight metrics; extra keys appear only when observed/configured. Irrigation duration, event counts and volume totals have distinct semantics. Continuous legacy averages are sample averages, not elapsed coverage.

## Authorization and concurrency

Both service entry points and HTTP routes require authenticated context and cultivation capability. Every mutation also requires a legacy cultivation write role and either `cultivation.manage_intelligence` or `cultivation.manage_connections`. Connection management additionally requires admin/dev. The service checks the durable active AppUser and resolves every reference under organization/facility scope. Browser-supplied tenant fields and all unknown body fields are rejected. Composite FKs constrain facility, canonical parents and new relationships; zone references also bind room identity. No composite SET NULL erases required tenant IDs.

PostgreSQL facility/record locks serialize cross-cycle membership and configuration changes. SQLite takes a write reservation with BEGIN IMMEDIATE. Conditional version updates reject stale requests. A unique partial index additionally prevents two open plant memberships. Cycles permit successive nonoverlapping half-open intervals; different cycles can share a room. A resolver never selects the first overlapping cycle arbitrarily. Initial mapping may establish an explicit historical interval. Subsequent remaps are future-effective only. Sensor channel mappings are immutable; duplicate registrations conflict rather than rewriting history or reactivating a device.

Approved recipes are immutable through the API and migration-installed database triggers, including updates, deletes and insertion into approved child collections. Approvals record AppUser and time. New edits use a new facility/name version. Targets are facility-defined and normalized; there are no agronomic defaults. Observations receive only the approved recipe/stage version effective at their timestamp. Future approval never retroactively establishes a historical target.

## Local evidence and imports

`gateway.py` uses `NormalizedExportAdapter` and the edge owner's `EdgeStore` exactly as documented in `CULTIVATION_EDGE_CONTRACT.md`. It contains no second spool or aggregation algorithm. `CULTIVATION_EDGE_PATH` is a host-owned setting, absent by default, and never accepted in HTTP bodies. Unconfigured imports fail with 503. Read summaries explicitly show unavailable evidence.

Authorization and scoped connection lookup run before constructing/parsing an adapter or opening the edge store. Imports are JSON arrays or CSV with documented exact columns, at most 1 MiB UTF-8 and 500 rows, with explicit metric/channel mappings. Preview does not persist readings. Commit verifies a scope/configuration/content/resolved-context digest. Device, mapping and sensor writes advance connection versions, invalidating previews. After a changed configuration, preview again; committing the same events preserves their first stored snapshots and unresolved evidence. Source identity is connection-qualified in the edge store. Unknown channels remain pending, conflicting identities remain disputed and replay does not drop pending evidence. Fixture/import activity never marks a connection live. Revocation blocks future ingestion and retains evidence.

Resolver context uses bounded set queries, then in-memory per-row decisions. Immutable snapshots include mapping revision, room/zone, approved recipe/stage and applicable cycle at observation time. No or multiple cycles retain room evidence with null cycle attribution; null is explicitly unassigned-or-ambiguous, not proof of no crop. Snapshot hold ends at the earliest known mapping/occupancy/stage boundary, capped to the configured local edge hold (five minutes by default). Later mapping changes do not rewrite snapshots. Live mapped exposure is not copied to every plant.

`/drain` means local pending-attribution retry and bounded rollup rebuild for the previous 24 completed UTC hours. It never drains raw observations to Supabase and never claims aggregate cloud publication. Explicit retention is available, but retention/outbox acknowledgement are not automatically invoked: without a durable aggregate receiver, evidence remains protected and quota backpressure is expected. The local commit and central count-only audit use different databases; if audit commit fails after local persistence, idempotent replay retains evidence and retries audit. This is recoverable, not a cross-database atomic transaction.

## Bounded decision support

Workspace uses set-based bounded queries, no provider calls and no per-room telemetry fetches. Room360 includes canonical plants, active cycles, zones, manual environment summary, recent operator events, canonical room Work links, and persisted local coverage/deviation summaries. Connection freshness is separate from measured coverage and environmental status. Local summaries are capped to 200 returned streams.

Cycle360 returns canonical membership/occupancy, exact linked harvest, events, cost provenance and cycle-filtered local summaries for at most eight most recent occupied rooms. All truncation is explicit. Exclusive exact harvest membership prevents a harvest's costs/yield being credited to multiple cycles. Only canonical harvest cost entries currently have proven cycle allocation; room/plant allocations, true COGS, revenue, grade and testing values remain unknown. Existing quality and material-lineage services are not replaced. Cycle detail reads canonical post-harvest batch status, direct harvest material transformations, their scoped output-lot links and structured quality summaries. It does not recursively traverse the downstream graph or load COA bodies. Empty summaries mean no matching bounded direct records, not a claim that all future downstream records are absent.

Plant exposure remains unknown until canonical movement intervals can prove location over time. A current room code or cycle membership is insufficient evidence. This candidate does not fabricate historical exposures.

## No-control and rollout gates

No equipment commands, automatic irrigation, automatic Work, plant movement, harvest consumption, inventory mutation, Metrc calls, new worker/scheduler or cloud service is introduced. Added recurring infrastructure cost is $0; local disk capacity/backup remains an operational requirement. Growlink live auth/endpoints/pagination/schema remain BLOCKED pending a reviewed vendor contract and customer credentials. There are no credentials here. This file-only candidate accepts no secret provisioning input; future live credentials must use existing encrypted IntegrationConfiguration storage, with an additive provider contract and administrator checks, never config JSON, hints, audit or exception bodies.

0086 is the single static additive successor to 0085. It preserves old observation rows, adds nullable original-evidence columns, named scoped FKs/indexes, browser-role denial, RLS, server runtime grants and approved-recipe guards. Downgrade refuses any new relationship or original evidence. The runtime receives SELECT/INSERT on all new tables and UPDATE only where the implemented lifecycle requires it; no DELETE. Its server-only RLS policy does not authorize browser access. Real PostgreSQL grants/trigger/locking acceptance belongs to the primary and is not established by SQLite tests.

Remaining release risks: actual PostgreSQL migration/ACL/locking validation; primary review of cross-database audit recovery and retention policy; authenticated public UI acceptance; protected PC release. Recursive downstream genealogy/COA detail hydration and proven historical plant exposure are not implemented by this bounded slice. Optional aggregate cloud publication and Growlink live transport are not implemented. No application release is claimed.

## Final backend integration additions

Implemented recipe targets include optional positive `threshold_seconds` (1..2678400). Approved recipe payloads, Room360 targets and immutable observation snapshots preserve the exact value. Missing thresholds are visibly `not_configured`: API summaries still expose measured above/below duration but suppress threshold-qualified alert intervals. Configured alerts require one continuous same-direction excursion. Disconnected excursions, unknown gaps and stage/context changes cannot be combined to satisfy the threshold. Recipe guards also reject moving a draft stage/target into an approved parent. Existing narrow runtime grants, exact-index migration validation and evidence-preserving rollback remain intact.

Preview digests now bind the scoped resolved snapshot list, including temporal mapping, occupancy, stage, recipe and target context, alongside content and connection version. Preview and commit each use the same bounded eight-query resolver snapshot; no per-reading SQL or provider calls are introduced. Commit holds the established facility mutation lock while checking context and persisting locally. A changed attribution requires another preview, and an equivalent retry preserves the first local raw snapshot.

Workspace adds grouped canonical active plant counts and bounded active cycle/stage context, without per-room requests. The singular stage is null for ambiguity or truncated context. Zone, device mapping and sensor child GET routes expose existing records. Plant360 now projects actual dated crop memberships, overlapping cohort occupancy links, canonical mother links, group membership and harvest references. Canonical parent joins additionally validate scope for legacy relationship tables. No per-plant telemetry copies are made. Membership and cohort room intervals do not establish individual occupancy; the individual exposure interval result remains unknown. Reconstruction and reconciliation of the canonical plant movement event chain is still future work.

Room360 and Cycle360 accept explicit aligned UTC historical summary windows and expose edge v2 semantic snapshots and attribution intervals, actual recipe standards and connection freshness separately from measured room conditions. Cycle occupancy detail returns the most recent 200 records in chronological display order. Connection freshness is scoped to each connection, explicitly not room-level condition; up to eight connection diagnostics are hydrated on these detail surfaces with a truncation flag. Receipt time, valid observation time and central import audit time remain distinct. No file import asserts live connected or current sensor proof. Import responses include bounded disposition identities/status/safe reasons, including quarantine; audit stores counts only.

## Local maintenance configuration and limits

The caller explicitly invokes POST rollup with UTC `start` and `end`, then reads Room360/Cycle360 with the same window. This works for manually imported historical evidence beyond the last 24 hours. The administrator evidence GET reads the same local store, with opaque pagination, and never publishes raw data centrally. Maintenance status shows diagnostics and limits. Retention preview is conservative (`eligible:null`) rather than pretending to calculate deletion eligibility; explicit execution delegates every prerequisite to EdgeStore. Pending, quarantined, disputed, missing-rollup and unacknowledged evidence remains protected.

Configure `CULTIVATION_EDGE_PATH` on the host, plus optional integer `CULTIVATION_EDGE_MAX_SCOPE_ROWS`, `MAX_SCOPE_BYTES`, `MAX_DISK_BYTES`, `MAX_BATCH`, `MAX_QUERY_ROWS`, `MAX_GAP_SECONDS`, `BUCKET_SECONDS` and `MAX_WINDOW_SECONDS` with the same `CULTIVATION_EDGE_` prefix. Unset values use the edge contract defaults. Gateway configuration caps these respectively at 1000000 rows, 1073741824 scope bytes, 4294967296 shared bytes, 500 batch items, 100000 query rows, 86400 gap seconds, 86400 bucket seconds and 2678400 window seconds. Every value must be positive; existing pinned bucket/gap settings cannot be changed in place. Per-request rollup windows additionally fit `max_batch * bucket_seconds`, so larger ranges require explicit successive aligned requests. These are resource ceilings, not crop standards. Quota exhaustion returns backpressure; collection is not promised indefinitely.

This adds $0 recurring infrastructure and no background service, scheduled task, provider transport or automatic maintenance. The explicit administrator `/archive` action now delegates to the concurrently completed edge-owned `archive_aggregates` receiver. Configure a pre-created absolute host-owned `CULTIVATION_EDGE_ARCHIVE_DIR`; request bodies cannot select a path. The receiver validates full scope, generation/hash and aggregate-only schema, durably writes separate immutable archive files, performs verified readback, and only then attempts exact clean-current revision acknowledgement. The backend does not implement a second receiver or accept arbitrary caller acknowledgements. Central audit records action and counts only. Archival never purges raw evidence; retention is a separate explicit action and still enforces every EdgeStore prerequisite.

Without archive configuration the exact exposed blocker remains `durable_aggregate_receiver_not_configured`; with configuration the prerequisite code is `requires_clean_verified_archive_and_resolved_evidence`. Configuration alone proves neither successful archival nor retention eligibility. Preview returns unknown eligibility and execution evaluates the actual prerequisites. No automatic cloud publication exists. Archive filesystem capacity, ACLs, backup and preservation after acknowledgement are host responsibilities. Tombstones and immutable aggregate revisions grow until an operator makes a storage decision. Default imports, rollups and drain do not invoke archival or retention.
Primary-owned edge follow-up resolved in the shared tree: the edge owner now suppresses missing-threshold alerts directly and exposes `outside_intervals` separately. Backend suppression remains compatible. The final edge contract also adds a verified local aggregate receiver, now wired through an explicit administrator action while default publication remains disabled. No edge source, adapters, independent acceptance/migration tests or scripts were changed by this backend integration. Persisted raw snapshots remain immutable; newly entered historical boundaries without a later resolved observation still require reconciliation, as documented by the edge contract.

## Final recipe-parent concurrency decision

Recipe stages cannot change their recipe ID, and recipe targets cannot change their stage ID, even while draft. A new facility recipe version creates new children. PostgreSQL and SQLite triggers enforce this without SECURITY DEFINER, stage UPDATE grants or additional runtime privileges. This closes nested stage-reparent races by making that relationship immutable. Child writers still lock the parent recipe in deterministic order and inspect the locked status before inserting or editing permitted draft evidence. Existing approved-version guards remain authoritative. Actual PostgreSQL approval/child-writer races run in the disposable CI gate, including both commit orders; the former draft-reparent test now asserts the stronger parent-identity invariant.

The locking contract follows PostgreSQL 17's documented FOR SHARE conflict with row updates and its returned-current-row behavior under Read Committed: https://www.postgresql.org/docs/17/explicit-locking.html and https://www.postgresql.org/docs/17/transaction-iso.html. No grant was expanded to resolve the race.

## Integration-discovered authentication correction

The disposable PostgreSQL matrix retains unrelated synthetic users before exercising the existing JWT acceptance suite. That exposed an existing account lookup ambiguity: an OR of canonical ID and email could return an unrelated blank-email or conflicting-email record first. Authentication now resolves the verified canonical ID first. Only a missing ID with one unambiguous nonempty legacy email match can use the existing compatibility path; an inactive exact identity never falls back to another account. Persisted role/facility checks, JWT issuer/audience/signature checks and production rejection of developer headers remain unchanged. No real users, credentials, memberships or account identities were modified.

Seven new isolated real-JWT regressions cover exact identity, missing/blank email, conflicting email, absent identity, inactive identity, legacy compatibility and ambiguity. The combined authentication, web-inventory, infrastructure and API-security suite passed 63 tests after the correction. These are test results, not production sign-in acceptance.
